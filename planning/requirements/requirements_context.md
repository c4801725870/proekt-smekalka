# Requirements Context — Smekalka

**Purpose:** Track requirements, specifications, and acceptance criteria.
**Last updated:** 2026-09-20

---

## What We Track Here

1. **Functional requirements** — what the system must do
2. **Non-functional requirements** — performance, security, scalability
3. **Constraints** — technical, business, regulatory
4. **Acceptance criteria** — how to verify a requirement is met

---

## Requirement Template

```markdown
### REQ-[NNN]: [Requirement Title]

- **Type:** [Functional / Non-Functional / Constraint]
- **Priority:** [Must Have / Should Have / Nice to Have]
- **Status:** [Draft / Approved / Implemented / Verified]
- **Source:** [Stakeholder, document, or conversation]
- **Date:** [YYYY-MM-DD]

**Description:**
[What the system must do]

**Acceptance Criteria:**
- [ ] [Criterion 1 — testable]
- [ ] [Criterion 2 — testable]
- [ ] [Criterion 3 — testable]

**Related:**
- Bugs: [B001, B002]
- Features: [F001]
- Tests: [TC-001, TC-002]
```

## Requirement Categories

| Category | Description | Examples |
|----------|-------------|---------|
| Functional | System behavior | "System ingests raw data from APIs" |
| Performance | Speed, throughput | "TRIZ resolution completes in < 60s" |
| Security | Auth, encryption | "No secrets logged to output" |
| Scalability | Growth handling | "Support concurrent multi-domain analysis" |
| Usability | UX requirements | "Human architect can override any decision" |
